# clptr4p setup (fresh install)

End-to-end path from a clean checkout to a running vault backing a Hermes
agent. Every secret you need is generated locally by `vault/bootstrap.sh`;
nothing here phones home. ASCII `--` only, per repo convention.

## What the secrets are (and what losing them costs)

| Secret | What it unlocks | Generated by |
|---|---|---|
| `VAULT_DEK` | AES-256-GCM encryption of `payload_encrypted` + HMAC provenance handles | `bootstrap.sh` |
| `GATEWAY_DATABASE_URL` | Postgres login for the gateway role -- this is the access credential the MCP server entry passes through | `bootstrap.sh` (password embedded in the URL) |
| `CAPTURE_DATABASE_URL` | Postgres login for the capture role (direct ingest CLI) | `bootstrap.sh` |
| `REVIEWER_DATABASE_URL` | Postgres login for the reviewer role (review/triage CLIs) | `bootstrap.sh` |
| `DATABASE_URL` | Postgres login for admin (migrations, ops) | `bootstrap.sh` |

**Back up `vault/.env` somewhere safe.** Losing the DEK means every encrypted
payload already in the vault is unrecoverable (claims stay readable, their
sealed source evidence does not). DEK rotation is not implemented. The `.env`
is written 0600; keep it that way.

## Requirements

- Docker (Postgres 16 + pgvector run in a container, loopback only)
- Deno (default path `~/.deno/bin/deno`; override with `CLPTR4P_DENO`)
- An OpenRouter API key (embeddings via `openai/text-embedding-3-small`)
- Hermes Agent, if you want the memory-provider integration

## 1. Vault

```
cd vault
./bootstrap.sh                    # generates .env: role passwords + VAULT_DEK + REVIEWER_PRINCIPAL
docker compose up -d --wait       # Postgres 16 + pgvector on 127.0.0.1:5433
set -a; . ./.env; set +a
deno run --allow-net=127.0.0.1:5433 --allow-env --allow-read=. migrate.ts
deno run --allow-net=127.0.0.1:5433 --allow-env verify_rbac.ts
                                  # expect: RBAC BOUNDARY OK (4 roles)
```

Edit `REVIEWER_PRINCIPAL` in `vault/.env` to your identity (it is stamped on
every review decision you make, e.g. `urn:user:you`).

**Policy note:** the migrations seed a starter `personal/3` policy (purpose
`retrieve.context`, a general-purpose selector set, 3600s retention, onward
disclosure forbidden) and leave `default-deny` inactive as the fail-closed
fallback. To change what your vault will serve, write a NEW numbered migration
under `vault/migrations/` that flips active to your version -- never edit
applied migrations, never stack policies (the table enforces exactly one
active row). See migrations 010-012 for the pattern.

## 2. Embeddings (OpenRouter key)

Claims are embedded at write time; embedding is transactional, so ingest and
review-approve FAIL without a working key (reads and proposals work fine
without it). Put the key where the vault resolves it:

```
# ~/.hermes/.env (recommended if you use the Hermes integration):
OPENROUTER_API_KEY=sk-or-...
# or just export it in the shell before ingest/review commands
```

## 3. Hermes provider integration

```
# a) install the plugin (user plugin directory):
mkdir -p ~/.hermes/plugins/clptr4p
cp provider/__init__.py ~/.hermes/plugins/clptr4p/__init__.py

# b) give Hermes the vault credentials (~/.hermes/.env):
#    copy GATEWAY_DATABASE_URL and VAULT_DEK from vault/.env
```

Add the MCP server entry to `~/.hermes/config.yaml` (adjust the repo path and
deno path to your machine):

```yaml
mcp_servers:
  clptr4p:
    command: /home/you/.deno/bin/deno
    args:
      - run
      - --allow-read=/path/to/clptr4p/gateway,/path/to/clptr4p/context-layer-reference
      - --allow-write=/path/to/clptr4p/vault/data
      - --allow-env
      - --allow-net=127.0.0.1:5433
      - /path/to/clptr4p/gateway/main.ts
    cwd: /path/to/clptr4p/gateway
    env:
      GATEWAY_DATABASE_URL: ${GATEWAY_DATABASE_URL}
      VAULT_DEK: ${VAULT_DEK}
    timeout: 60
```

The env passthrough is what hands the gateway its DB access -- there is no
separate MCP auth token; the role password inside `GATEWAY_DATABASE_URL` is
the access key.

Activate the provider (restart Hermes afterwards):

```yaml
memory:
  provider: clptr4p
```

The provider also honors `CLPTR4P_DENO`, `CLPTR4P_GATEWAY_ENTRY`,
`CLPTR4P_SUBJECT` (default `vault://subjects/primary`), and
`CLPTR4P_SELECTORS` (comma list of predicates to prefetch; default is the
full granted set of the shipped starter policy).

Verify the integration end to end:

```
HERMES_HOME=~/.hermes python3 scripts/verify_provider.py
# expect: PROVIDER VERIFY OK
```

## 4. First memories + review workflow

Two ways in:

- **Curated import** (batch, trusted): write a capture envelope
  (`vault/fixtures/` has examples; the fields are documented in
  `vault/capture/types.ts`), then
  `deno run --allow-net=127.0.0.1:5433,openrouter.ai --allow-env --allow-read=.,capture ingest.ts fixtures/your-file.json`
  from `vault/`.
- **Agent proposals** (zero-trust): the agent calls `clptr4p_propose`, or a
  builtin memory-tool write gets mirrored; either way it lands in the review
  queue as `pending_validation` and commits nothing until you approve.

Review the queue (one command; sources `vault/.env` itself):

```
scripts/review.sh list
scripts/review.sh show <id>
scripts/review.sh approve <id>
scripts/review.sh reject <id> --reason "text"
```

Auto-triage closes the dead weight first (`vault/triage.ts` -- reject-only by
construction, so it can never bypass your approval):

```
scripts/triage_digest.sh    # daily digest form; silent on an idle queue
```

For a daily nudge, schedule `scripts/triage_digest.sh` as a no-agent cron job:
empty stdout sends nothing, survivors arrive with ready-to-paste commands.

## 5. Smoke-test your install

From `gateway/` with `vault/.env` sourced:

```
deno task check && deno task test
bash tests/smoke.sh && bash tests/smoke_pg.sh
bash tests/smoke_capture.sh && bash tests/smoke_review.sh
bash tests/check_policy.sh
```

Expect `... OK` from each. For the triage layer: `bash tests/smoke_triage.sh`
(note: triage processes the whole pending queue, so a run also closes any
real dead-on-arrival proposals -- that is the point).

## 6. Backup and restore

```
scripts/vault_backup.sh                     # -> vault/backups/clptr4p-vault-<ts>.tar.gz.enc
scripts/vault_restore.sh --list <file>      # manifest + row counts, no writes
scripts/vault_restore.sh --add <file>       # non-destructive merge (add-or-keep)
scripts/vault_restore.sh --replace <file>   # destructive rebuild (confirmed)
```

A backup contains `vault.pgdump` (schema + data + embeddings, pg_dump custom
format), `env.txt` (a copy of `vault/.env` -- login-role passwords are
cluster-level and NOT carried by a dump, so the backup ships them to be
self-sufficient), and a manifest. The tar.gz is encrypted with openssl
AES-256-CBC/PBKDF2 (600k iterations) with a sha256 sidecar; `--keep N`
prunes to the newest N (default 30).

Passphrase: `VAULT_BACKUP_PASSPHRASE` if set, else `VAULT_DEK`. The DEK
fallback means a backup is decryptable wherever `vault/.env` exists -- fine
for local copies, but for off-machine disaster recovery set an independent
`VAULT_BACKUP_PASSPHRASE` so one leaked file does not open both doors.

- `--add` merges missing rows into the live vault (`ON CONFLICT DO NOTHING`;
  live rows always win). Backup policies import **inactive** so the live
  active policy stays active. Idempotent: re-running against the same vault
  is a no-op. The merge runs via postgres_fdw against a scratch DB, fully
  transactional with ON_ERROR_STOP.
- `--replace` renames the live DB aside, restores into a fresh DB, re-runs
  migrations, and drops the old DB only on success (failed pg_restore rolls
  back to the pre-restore state). It terminates live connections first (the
  gateway reconnects). If the backup's `.env` differs from yours (fresh
  machine), the script prints how to align the login-role passwords.

Vault zone integrity note: `--replace` uses `--no-owner` restores into an
admin-owned database, then migrate.ts; RBAC grants are carried in the dump.
Run `deno run ... verify_rbac.ts` after any restore.

Backups contain vault secrets: `vault/backups/` is gitignored -- keep the
destination private and 0600.
